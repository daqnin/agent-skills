# Evidence And Limits

On 2026-10-20 the no-admin r4 package was exercised on the source Windows 11 x64 host with administrator-role check false. Vendor binaries had valid signatures and unchanged hashes. Xftp reached its Free for Home/School main window after original free-license values were included. Xshell passed the Personal license check and created its main/child frame; package XshellCore paths were checked. The parent's and child's HKLM sentinel reads returned current-user shadow data. The initial archive contained 227 manifest entries plus manifest, no enclosing directory and no administrator helpers.

The source machine already had both products installed. Real machine registration was left intact. Process routing and the synthetic no-HKLM sentinel establish isolation behavior but do not prove a separate clean computer or another hardware identity will accept the original free license. No separate clean Windows machine, ARM64, Windows 10, offline license validation, settings migration after normal exit or broad antivirus behavior was accepted in that run.

Retain this distinction in delivery reports. A new run should record its own versions, signatures, non-elevated token, probe, archive checks and actual GUI results. Do not reuse historical acceptance as proof of a newly changed binary or product version.

## 2026-11-04 same-host run (Xshell/Xftp 8.0.0119, binary 8.0.0.27 built 2026-10-14, Windows 11 25H2 build 26200)

The package was rebuilt with native x86 GUI-subsystem launchers and a self-checking Xftp path probe. Verifier passed: 228 manifest files, ZIP/staging hashes, rootless layout, only Xshell-Portable.exe / Xftp-Portable.exe at the root, unchanged vendor exe hashes, sanitized profiles, parent/child isolation (two `user-only` reads), and three portable path assertions (HKLM Xftp/Xshell `...\8\Path`, HKCU `Common\8\UserData\UserDataPath`); real HKLM Xftp Path was unchanged.

Verified GUI: `Xftp-Portable.exe` started the package's Xftp.exe, loaded registry-bridge.dll and showed `桌面 - Xftp 8 (Free for Home/School)`; it stayed open until a normal WM_CLOSE. `Xshell-Portable.exe` resolved to the package Xshell.exe, loaded the bridge, seeded the isolated namespace and exported Data/registry.clixml on normal exit; the real HKCU UserDataPath was never changed. No cmd.exe, WSH or VBS was involved.

Not achieved: without `-PreservePersonalRegistration` Xshell showed a #32770 "产品运行所需…请重新安装 Xshell" dialog and kept the frame hidden (40002-class missing product identity). With the user's existing Personal free registration, `Check Personal License` succeeded and the log recorded `Created Xshell main window`, `Toolbars are created.` and `Xshell main window is ready.`, but `Execute Core Process` was followed by `Create Child Frame Result : 0`, `MainFrame Create Failed`, `Failed to initialize viewer instance.` and `Exit Xshell...` after about five seconds. Two XshellCore.exe children from the package were observed and neither ever loaded registry-bridge.dll; no XshellCore log was produced; the frame never became visible, so Ctrl+Alt+F could not be delivered and no Xftp.exe appeared. By contrast, the installed Xshell's earlier same-host log shows `Create Child Frame Result : 1`, a XshellCore log and a ~52 second session.

Therefore the "built-in Xftp button inside Xshell" UI path was NOT accepted on this build. Tools/xftp-path-probe.exe proves that an injected process resolves Xftp's product path to the package, and the isolation probe proves ordinary CreateProcess children are injected; neither proves a COM/other viewer child is injected or that the Xftp button works. Treat Xftp-Portable.exe as the reliable entry point. Do not describe the button path as verified. Adapting to this build likely requires covering the viewer child launch path (for example a COM local-server activation), which is unverified here.

This run is same-host, non-elevated, with both products already installed and the user's own free registration copied into a private local package. It is not clean-machine, cross-machine licensing, offline activation, other Windows versions, ARM64 or other product builds acceptance.

## 2026-11-04 follow-up: viewer launch path, stale overrides, and the core crash

Static import analysis: `Xshell.exe` imports `ShellExecuteExW`/`ShellExecuteW` and `XshellLib.dll` imports `WinExec`, besides `CreateProcessW`. A traced bridge recorded `PATCH CreateProcessW` on ten modules but **zero** `hookProcessW` calls, while `SHELLEXEC_EX_W` fired with `lpParameters = -setviewer <hwnd>`, `fMask=0x140`, `nShow=0`, `lpDirectory=NULL`. The viewer is therefore launched through `ShellExecuteExW`, which bypassed the original CreateProcess-only IAT hook. The bridge now hooks `ShellExecuteW/A`, `ShellExecuteExW/A` and `WinExec`, reimplementing them as suspended-start + bridge injection + resume while preserving parameters and using the executable's folder as working directory when `lpDirectory` is NULL. A second `ATTACH` from the `XshellCore.exe` child confirms it now loads `registry-bridge.dll`.

Two stale overrides were removed: the bridge forced `MultiCoreProcess=0` via a `RegQueryValueExW` hook, and `build.ps1` forced INI `SingleProcessMode=1`. The installed product has `MultiCoreProcess=1`, `SingleProcessMode=0` and logs `Option: Multi Core Process Mode`; the portable package logged `Single Core Process Mode`. Removing both restores the vendor's mode, and `portable-user.ps1` now re-applies the original `MultiCoreProcess` from `Data/settings.clixml` on every start.

Even after these fixes, `Create Child Frame Result : 0` / `Failed to initialize viewer instance.` persists on binary 8.0.0.27. A process-lifetime watcher recorded `CORE_EXIT code=0xC0000005` (access violation) for the first `XshellCore.exe`, which also spawns a second short-lived `XshellCore.exe`; neither produced a `XshellCore_*.log`. A control build with all launch hooks disabled (core NOT injected) produced the same `0xC0000005` exit, so the crash is inherent to this portable configuration on this build, not a side effect of injection. A/B builds that skipped IAT patching inside the core, and that disabled the instance-isolation hooks (`CreateEventW`/`OpenEventW`/`EnumWindows`/`FindWindow*`), both still failed. The package's `App\Xshell 8` tree is a superset of the source install (123 vs 117 files), so missing resources are excluded.

Therefore the built-in Xftp button remains NOT accepted, and this is a hard boundary rather than an untried idea: fixing it would require vendor-level or deeper virtualization work plus a new real-machine test. Path portability (extracting to a different folder) was tested separately and is distinct from another hardware identity, offline license validation, ARM64, other Windows versions and other product builds, which remain unverified. A preserved-registration package may be copied only to the same licensed individual's additional personal device; a package without identity fields needs that person's own free license. This follows the vendor's published ver8 free EULA.
