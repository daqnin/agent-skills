# Portable Xshell And Xftp

Make a private, installation-free package from existing signed version 8 programs. Keep settings, exclude connection information, and support a destination without administrator rights. The verified implementation uses x86 vendor programs on x64 Windows. Other majors or architectures require separate adaptation.

## Workflow

1. Discover installed paths from uninstall entries and running process paths. Read the profile path from `HKCU\Software\NetSarang\Common\8\UserData\UserDataPath`, falling back to Documents. Inspect versions and executable signatures. Do not print session contents, license values or complete logs; report names, types and verification results only.
2. Read [workflow.md](references/workflow.md) before building. It contains compiler acquisition, exact commands, settings boundaries, runtime behavior and GUI acceptance. Use explicit source paths and a fresh output directory.
3. Run `scripts/compile-bridge.ps1` with an x86 TinyCC executable and a fresh cache output directory. It compiles the bridge DLL, runner, isolation probe, GUI-subsystem launcher and a self-checking Xftp path probe. Run `scripts/build.ps1` with `-BridgeDirectory` pointing at those compiled helpers. This option selects the no-admin launcher, bundles signed Microsoft x86 runtime DLLs beside each application, and emits `Xshell-Portable.exe` / `Xftp-Portable.exe` as the only double-click entry points.
4. Add `-PreservePersonalRegistration` when the user requests their existing free registration. Require original `Type=Personal`. Copy original identity and license fields without altering them. Never create license tokens, change expiration, spoof machine identifiers or bypass vendor validation. Do not package commercial activation. A preserved package contains private name/email and authorization data: the vendor free license permits one person on one desktop plus one additional personal mobile device for non-commercial home/educational use, so it may be copied only to that same person's second device, never given to another person. Without the switch, build an identity-free package; the other person must obtain their own free license through the vendor's official flow.
5. Run `scripts/verify-package.ps1` against the fresh output and ZIP. Run its `-RunProbe` option to test parent/child registry routing plus portable Xshell/Xftp product-path resolution, and to confirm the real HKLM Xftp path was not rewritten, all without launching either product. Test GUI startup only from a separate extracted test copy, without connections. Never repack the tested copy: it accumulates logs, registry state and new sessions.
6. Deliver the rootless software ZIP, SHA256 and actual verification limits. If updating this skill, run skill-creator's validator and export source helpers only. Neither vendor binaries nor private registration belongs in the skill archive.

## Essential Constraints

- The delivered no-admin package must not include `Register-Personal.cmd`, `register-personal.ps1`, any `.cmd`/`.vbs` launcher, an elevation path, or a containing top-level ZIP directory. Legacy scripts remain implementation dependencies of the older builder branch; do not select that branch for this workflow.
- `App/Xshell 8/Xshell.exe` and `App/Xftp 8/Xftp.exe` are not entry points. They need `NS_PORTABLE_REGISTRY` plus the injected bridge, so double-clicking them bypasses isolation and can read or write the installed product's registry. Making the vendor binaries self-launching would require a DLL proxy (side-loading) or an import-table change plus an environment-independent bridge; that path is unverified, may break signature/integrity checks and may be blocked by Windows protections. Do not promise it or disable protections to force it.
- NetSarang HKLM/HKCU paths are routed in the application processes into a dedicated current-user namespace. Installed profiles and real HKLM are not replaced. This is compatibility tooling, not a security sandbox. Do not disable Windows protections if bridge loading is blocked.
- Preserve the source INI `SingleProcessMode` and registry `MultiCoreProcess` values. On Xshell 8 build 8.0.0.27, forcing `SingleProcessMode=1` / `MultiCoreProcess=0` selects "Single Core Process Mode" and breaks the viewer handshake; the installed product uses `0` / `1` and logs "Multi Core Process Mode". Instance isolation comes from scoped window lookup and suffixed named events instead.
- Retain the builder's preference allowlists. Exclude sessions, credentials, SSH keys, host keys, master passwords, history, bookmarks, scripts, executable quick commands and restored windows. Default session templates must be reconstructed from display sections.
- On failed startup, inspect the filtered logs and actual child executable paths. Stop test processes only after verifying they belong to the test directory. Do not close installed connected sessions to make a test pass.
- Use [validation-boundary.md](references/validation-boundary.md) when explaining proven behavior. Same-host non-admin startup is not clean-machine or cross-machine authorization acceptance. If the vendor rejects the copied free registration, use its official free-registration flow.
- Do not present the built-in Xftp button as GUI-verified. On Xshell 8 build 8.0.0.27 the `XshellCore.exe` viewer is launched through `ShellExecuteExW` (`-setviewer <hwnd>`), not `CreateProcessW`. The bridge now hooks `ShellExecuteW/A`, `ShellExecuteExW/A` and `WinExec` and reimplements them as suspended-start + injection + resume, so the viewer child does load `registry-bridge.dll`. It nevertheless terminates with `0xC0000005` before creating a child frame; a control build without those hooks crashes identically, so injection is not the cause. `Xftp-Portable.exe` is the supported entry point. For an in-Xshell alternative, add a custom button/quick command that launches it. A diagnostic bridge built with `-DBRIDGE_TRACE` writes `%TEMP%\ns-bridge-trace.log`; never ship that build.
